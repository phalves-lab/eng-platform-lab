# eng-platform-lab

Laboratório da esteira de engenharia: gates, segurança, review de IA com contexto de negócio e merge queue, rodando sobre um app sintético de solicitações de campanha. Nada aqui é código ou dado de empresa.

## Stack

- Node 22, TypeScript strict, npm workspaces
- API: Fastify 5, Zod 4, Postgres via `pg` (migrations SQL em `apps/api/migrations`)
- Testes: Vitest com cobertura v8; Postgres real no CI
- Bot de review: Gemini API, Atlassian somente leitura (local), GitHub API só para comentar

## Arquitetura

- `apps/api/src/domain`: regras de negócio puras, devolvem `Result`, sem dependência de framework.
- `apps/api/src/http`: traduz HTTP para o domínio; `src/db`: repositório Postgres e migrations.
- `tools/review-bot`: monta contexto (task, critérios de aceite, módulo do catálogo, documentação, diff), revisa em 3 camadas, verifica achados graves e publica comentário fixo.
- `tools/eng-metrics`: coletor só leitura (GitHub e tasks) que calcula fila, alertas e métricas e publica o `data.json`. O contrato do arquivo fica em `src/contract.ts`.
- Resumo diário: `npm run digest -- --data <data.json>` monta o texto; o workflow `digest` roda às 9h em dia útil e só envia a um canal se o secret `DIGEST_WEBHOOK_URL` existir.
- `apps/portal-api`: API do portal em NestJS. Configuração validada com Zod no boot (falha se o modo de autenticação de desenvolvimento for usado em produção), guard global de autenticação (modo `dev` local ou token do Entra ID validado por JWKS), limite de requisições, módulos de handbook, review, pergunta e métricas de review (`GET /api/metrics/review`).
- Pergunte com modelo: `POST /api/ask/stream` responde por SSE (eventos `start`, `tool`, `delta`, `done` e `error`, contrato em `packages/contracts`) e `POST /api/ask` devolve o mesmo resultado em JSON. Com `PORTAL_LLM_BASE_URL`, `PORTAL_LLM_API_KEY` e `PORTAL_LLM_MODEL` (gateway compatível com a API de chat completions da OpenAI), o modelo responde usando as ferramentas do handbook (`packages/handbook/src/tools.ts`, as mesmas do servidor MCP), com timeout (`PORTAL_LLM_TIMEOUT_MS`) e limite de rodadas de ferramenta (`PORTAL_LLM_MAX_TOOL_ROUNDS`). Sem essas variáveis, ou se o modelo falhar antes de escrever, vale o modo busca. A pergunta sai com e-mail, CPF, telefone, cartão (só com dígito verificador válido) e RA de aluno (`RA` seguido de 9 dígitos) mascarados; o prompt de sistema versionado fica em `apps/portal-api/prompts/chat.md`. Testes usam só o provider roteirizado (`test/fake-provider.ts`), nunca modelo real.
- Modos do chat (rascunhos): `POST /api/ask/stream` aceita `mode` (`ask`, `refine-task`, `pr-description`, `release-notes`, `adr`, `weekly-summary`; contrato em `packages/contracts/src/chat-modes.ts`) e `GET /api/ask/modes` lista os modos com rótulo, exemplos, limite de texto (500 caracteres no Perguntar, 8.000 nos rascunhos), disponibilidade e a skill do marketplace que cada um representa. Cada rascunho usa as regras comuns de `apps/portal-api/prompts/draft-rules.md` e o prompt versionado `apps/portal-api/prompts/modes/<modo>.md` (o de descrição de PR recebe `.github/pull_request_template.md`); a descrição da skill (`lab-grill/grill`, `lab-taskforge/taskforge`, `lab-changelog/release-notes`) vem do catálogo de IA e, sem catálogo, o modo segue só com o prompt. Definições em `src/ask/modes/mode-definitions.ts`. Ferramentas só leitura dos rascunhos em `src/ask/tools/portal-tools.ts`: `metricas_review` (sem carga nem pares por pessoa), `metricas_fluxo`, `metricas_dora`, sobre os mesmos serviços das rotas de métricas, e `tarefa`, que lê as tasks de exemplo de `PORTAL_TASKS_DIR` (padrão `fixtures/jira`). Tudo é rascunho: nenhuma rota escreve em Jira, GitHub ou handbook. Sem modelo, os modos de rascunho ficam indisponíveis e respondem com aviso, sem cair na busca. A conversa guarda o modo em que começou (`chat_conversations.chat_mode`, migration `010`) e continua nele. O modelo de ADR do handbook fica em `handbook/04-modelo-adr.md`.
- `apps/portal-web`: front do portal em Next.js 15 com shadcn/ui no estilo do template de dashboard, menu lateral recolhível e busca com Ctrl K. Só conversa com a `portal-api`, pelo servidor (`src/lib/api.ts`). Os tokens de cor seguem os nomes do `@martech/design-system`; na Cogna, troca-se o bloco de tokens pelo do pacote.
- Releases no portal (`/releases`): projetos cadastrados em `catalog/releases/*.yaml` (schema em `packages/contracts/src/releases.ts`), prévia só de leitura montada pela `portal-api` em `src/releases` (regras puras em `rules.ts`, cliente GitHub REST só com GET). Exige `PORTAL_GITHUB_TOKEN` no ambiente da API; sem ele, as rotas do GitHub respondem 503. `PORTAL_RELEASES_DIR` troca a pasta do catálogo.
- Gerar e acompanhar release (`/releases`): `POST /api/releases/plan` monta o plano de escrita sem cache (PR direta da origem ou branch `release/AAAA-MM-DD` criada do SHA da origem, conforme o `mode` do cadastro; duas PRs ligadas no corpo quando front e back estão em repositórios diferentes, uma só no monorepo; corpo no template de `plan-rules.ts` com tasks, autores, ordem de deploy e checklist único de SQL e ENV; PR de release aberta é atualizada em vez de duplicada) e `POST /api/releases/execute` só escreve se o plano refeito tiver o mesmo hash e cada repositório for digitado igual. Só papel `lead` ou `admin` planeja e executa; `dev` vê a prévia, o acompanhamento e o histórico. Toda escrita passa pela porta `GitHubWriter` (`github-writer.ts`), que só cria branch `release/*` nova, abre PR, edita o corpo, aplica rótulos, atribui autores e cria tag e GitHub Release: nunca push em branch existente, nunca merge. `GET /api/releases/tracking` mostra resumo por IA (`release-summary.yml`), CI, aprovações e merge das PRs abertas pelo portal; depois do merge, `POST /api/releases/publish/plan` e `/publish/execute` criam a tag e a release com as mesmas travas. A auditoria fica na tabela `release_runs` (migration `005`), então gerar, acompanhar e publicar exigem `DATABASE_URL`. A escrita só liga com `PORTAL_RELEASE_WRITE_ENABLED=true` (padrão `false`), que exige `PORTAL_GITHUB_WRITE_TOKEN` e `DATABASE_URL`; desligada, a execução responde 403 e registra a recusa. Testes usam só o GitHub falso (`test/fake-github.ts` e `test/fake-github-writer.ts`), nunca a API real.
- `packages/handbook` e `packages/contracts`: leitor do handbook e schemas Zod compartilhados entre API, front e servidor MCP. Em desenvolvimento são lidos pelo código-fonte (condição `@lab/source`); no build, pelo `dist`.
- `packages/catalog`: leitor do catálogo de IA. Lê um marketplace no formato do Claude Code (`.claude-plugin/marketplace.json`, `plugin.json` e `SKILL.md` de cada plugin) na pasta de `PORTAL_MARKETPLACE_DIR` (padrão `fixtures/marketplace`, sintético) e junta com o overlay versionado em `catalog/ai/` (`plugins.yaml` com maturidade, dono e revisão; `mcps.yaml` com os MCPs homologados), pasta trocável por `PORTAL_AI_CATALOG_DIR`. Plugin sem overlay aparece como `draft`, sem dono.
- Rodar o portal local: `npm run panel -- --only-demo --out "$PWD/.portal-data"`, `npm run build --workspace @lab/portal-api`, `PORTAL_HANDBOOK_DIR=$PWD/handbook PORTAL_PANEL_DATA=$PWD/.portal-data/data.json node apps/portal-api/dist/main.js` e `PORTAL_API_URL=http://localhost:4100 npm run dev --workspace @lab/portal-web`.
- `packages/database`: pool `pg`, runner de migrations SQL versionadas (`packages/database/migrations`, tabela de controle `portal_schema_migrations`, lock consultivo e checksum por arquivo) e repositórios tipados com Zod: `metric_snapshots`, `jira_issues`, `jira_status_changes`, `jira_sprints`, `jira_sprint_issues`, `deploys`, `incidents`, `chat_conversations`, `chat_messages` e `release_runs`. Migration nova só expande o schema; o teste `migrations.test.ts` barra `DROP`, `RENAME`, troca de tipo e coluna `NOT NULL` sem default. `@lab/database/testing` cria um schema descartável por arquivo de teste.
- `apps/portal-worker`: worker de coleta. Cada coletor implementa `Collector` (`name`, `schedule`, `run(ctx)`); o agendador roda no boot e a cada intervalo, sem sobrepor execuções do mesmo coletor, com log em JSON por linha. O coletor `eng-metrics` usa `collectPanelData` do `tools/eng-metrics` e grava o snapshot do dia (fuso `WORKER_TIMEZONE`) em `metric_snapshots`. O coletor `chat-retention` aplica a retenção do histórico do Pergunte. Configuração validada com Zod: `DATABASE_URL`, `WORKER_INTERVAL_MINUTES` (padrão 60), `WORKER_CHAT_RETENTION_DAYS` (padrão 90), `WORKER_DATASETS` (`lab`, `demo`), `WORKER_TASK_SOURCE` e as credenciais do GitHub quando o conjunto `lab` está ligado. O worker aplica as migrations no boot.
- Histórico do Pergunte: com `DATABASE_URL`, cada resposta do `POST /api/ask/stream` fica guardada em `chat_conversations`, `chat_messages` e `release_runs` (migration `004`), com pergunta, resposta e título já mascarados, ferramentas usadas, fontes e modo (`llm` ou `retrieval`); o stream termina com um evento `conversation` e aceita `conversationId` para continuar a conversa, mandando os últimos 6 turnos ao modelo. `GET /api/conversations`, `GET /api/conversations/:id` e `DELETE /api/conversations/:id` só enxergam as conversas da própria pessoa; sem banco, respondem 503 e o chat segue sem guardar. O worker apaga conversas paradas há mais de `WORKER_CHAT_RETENTION_DAYS` dias (padrão 90).
- Coletor do Jira no worker (`apps/portal-worker/src/collectors/jira/`): porta `JiraSource` com adaptador fixture (`fixtures/jira-board/`, projetos fictícios `LAB` e `OPS`) e adaptador Jira Cloud só leitura (busca JQL com changelog, agile API para sprints, `Retry-After` em 429). Grava issues, transições, sprints e a participação de cada issue nas sprints (`jira_sprint_issues`) com upsert idempotente. O mapa de status para categoria fica em `catalog/jira/workflow.yaml` e é lido por `packages/flow`. Rodar uma vez com a fixture: `DATABASE_URL=postgres://lab:lab@localhost:5433/lab npm run collect:jira -w @lab/portal-worker`; no worker agendado, ligar com `WORKER_JIRA_SOURCE=fixture` ou `cloud` (detalhes em `apps/portal-worker/README.md`). O portal não escreve no Jira.
- Métricas de fluxo (`packages/flow`): funções puras sobre o espelho do Jira, com o workflow de `catalog/jira/workflow.yaml` aplicado na leitura. Entregas por semana, tempo de ciclo (do primeiro movimento até concluído) e lead time (da criação até concluído) em p50, p85 e p95 por posto mais próximo, WIP, idade dos itens em andamento (atenção acima do p50 e atrasado acima do p85 do tempo de ciclo), bloqueios ativos e tempo bloqueado. Épicos ficam fora; status sem categoria conta como a fazer e aparece na resposta. A `portal-api` expõe `GET /api/metrics/flow?project=&component=&weeks=` (só com `DATABASE_URL`; sem dados do Jira responde 503; `PORTAL_JIRA_WORKFLOW` troca o arquivo do workflow) e a tela `Entregas > Fluxo` mostra KPIs, entregas por semana, distribuição do tempo de ciclo, itens envelhecendo e bloqueados com link para o Jira.
- Boards por área: `GET /api/boards` lista os projetos do espelho e `GET /api/boards/:project` devolve o kanban só de leitura com as colunas do workflow (concluídos dos últimos 14 dias), o fluxo cumulativo diário de 8 semanas, o previsto contra entregue da sprint ativa e das 3 anteriores (previsto é o que estava na sprint no início, pela data de entrada em `jira_sprint_issues`) e o progresso dos épicos. Regras em `packages/flow/src/board.ts`; tela `Entregas > Boards`. Nenhuma rota escreve no Jira.
- Scorecard por repositório (`/qualidade/scorecard`): repositórios em `catalog/repos/*.yaml` (`source: github` lê a API do GitHub; `source: fixture` usa sempre a fixture sintética `fixtures/scorecard/<id>.json`) e, em `catalog/scorecard/policy.yaml`, o peso e o padrão do handbook de cada checagem, as versões de Node aceitas, a idade máxima do `AGENTS.md`, a penalidade por alerta e as faixas de nível. O coletor `scorecard` do worker roda as regras puras de `apps/portal-worker/src/collectors/scorecard/checks.ts` e grava `.portal-data/scorecard.json`. O adaptador GitHub só faz GET com `GITHUB_TOKEN`; 403 numa leitura opcional vira checagem "sem leitura", fora da nota, e limite de requisições falha só aquele repositório. A API serve o arquivo de `PORTAL_SCORECARD_DATA` (padrão `.portal-data/scorecard.json`) em `GET /api/quality/scorecard` (filtros `term` e `level`) e `GET /api/quality/scorecard/:id`; sem arquivo, 503.
- Documentação com validade (`/qualidade/documentacao`): cada arquivo do handbook tem `dono` e `revisado_em` no frontmatter, e um padrão pode ter `- **Dono:**` e `- **Revisado em:**` próprios (o que faltar vem do arquivo). `packages/handbook` lê isso em `reviewItems` e classifica em `assessReview`; `GET /api/quality/docs` agrupa por dono e marca como vencido o que passou de `PORTAL_DOCS_MAX_AGE_MONTHS` meses (padrão 6, ou `?months=`), como vencendo o que vence em 30 dias e à parte o que não tem dono ou data.
- `apps/portal-api` com `DATABASE_URL` lê o snapshot mais recente de cada conjunto no banco; sem ela, lê o `data.json` de `PORTAL_PANEL_DATA`. Sem snapshot gravado responde 503.
- DORA (`Entregas > DORA`, `GET /api/metrics/dora?team=&repo=&weeks=`): `packages/dora` lê o cadastro `catalog/dora/repos.yaml` (repositório, time, sistema, ambiente de produção, branch padrão e fonte dos deploys: `fixture`, `github-deployments` ou `github-workflow`), os incidentes versionados em `catalog/incidents/*.yaml` (id, título, sistema, severidade, início, fim e deploy causador opcional) e as fixtures sintéticas de `fixtures/dora/`, e calcula em funções puras as 4 métricas por repositório e por time, com a faixa do relatório DORA de 2023 (`src/bands.ts`). Regras: deploy com status `failure` não chegou a produção e fica fora da frequência e da taxa de falha; falha de mudança é deploy revertido ou citado como causa de incidente; lead time vai do primeiro commit do PR ao primeiro deploy em produção que contém o merge; incidente sem causa conta para todos os repositórios do sistema. O coletor `dora` do worker grava deploys (com os commits que cada um levou), PRs mergeados (`delivery_changes`, migration 006) e incidentes; o adaptador GitHub só faz `GET`. A API calcula a partir do banco com `DATABASE_URL` e, sem ela, direto das fixtures. Pastas trocáveis por `PORTAL_DORA_CATALOG`, `PORTAL_INCIDENTS_DIR`, `PORTAL_DORA_FIXTURES_DIR` (API) e `WORKER_DORA_CATALOG`, `WORKER_INCIDENTS_DIR`, `WORKER_DORA_FIXTURES_DIR` (worker).
- Registro de deploy: o workflow reutilizável `.github/workflows/deploy-event.yml` (entrada `status`, `environment`, `sha`) roda `npm run deploy-event`, que cria um deployment do GitHub com o status final; reversão vai na descrição (`eng-metrics:rolled_back`), porque o GitHub não tem esse estado. Para conferir sem chamar o GitHub: `npm run deploy-event -- --repo lab-demo/campanhas-api --sha abc1234 --status success --dry-run`.
- `handbook/`: padrões numerados, sistemas, glossário e decisões pendentes do laboratório, no mesmo formato do handbook do time.
- `tools/mcp-context`: servidor MCP só de leitura sobre o handbook (ferramentas `regras_para_ia`, `padrao`, `buscar_padroes`, `sistema`, `buscar_sistemas`, `glossario`, `decisoes_pendentes`, `buscar`). Lê `handbook/` por padrão ou a pasta em `MARTECH_HANDBOOK_DIR`. Para registrar no Claude Code, no Kiro (já configurado em `.kiro/`) e em outros clientes, veja `tools/mcp-context/README.md`.
- `apps/panel`: app do painel (Vite, React e shadcn/ui), estático, lê só o `data.json` publicado ao lado. Componentes do shadcn ficam em `src/components/ui`. Para rodar local: `npm run panel -- --only-demo --out "$PWD/apps/panel/public"` e `npm run dev --workspace @lab/panel`.
- `review/`: prompts versionados, rubrica e golden set. `catalog/modules/`: dono, tier e caminhos de cada módulo. `policy/`: rulesets, risco, Semgrep e política de IA.
- `fixtures/`: tasks e páginas sintéticas usadas no CI.

## Comandos

- Instalar: `npm ci`
- Dev da API: `npm run dev -w @lab/api` (exige `DATABASE_URL`)
- Postgres local: `docker compose up -d` sobe o Postgres 16 na porta 5433 (volume `portal-db`, usuário, senha e banco `lab`). Use `DATABASE_URL=postgres://lab:lab@localhost:5433/lab` para os testes de integração e o worker; sem essa variável os testes de banco são pulados. Para zerar: `docker compose down -v`.
- Worker: `DATABASE_URL=postgres://lab:lab@localhost:5433/lab WORKER_DATASETS=demo npm run worker -w @lab/portal-worker -- --once` (sem `--once`, fica agendado até `SIGINT` ou `SIGTERM`).
- Coletor do Jira uma vez, com a fixture: `DATABASE_URL=postgres://lab:lab@localhost:5433/lab npm run collect:jira -w @lab/portal-worker`
- Scorecard uma vez, sem banco: `npm run scorecard -w @lab/portal-worker` (fixtures; `-- --source github` lê o GitHub com `GITHUB_TOKEN`; `-- --out <arquivo>` troca a saída). No worker agendado, o coletor liga com `WORKER_SCORECARD_OUT`.
- Gate completo (mesmo do CI): `npm run verify`
- Testes: `npm test`; cobertura do diff: `npm run diff-coverage -- origin/develop`
- Prompt do bot sem chamar modelo: `npm run review -- review --repo-dir "$PWD" --config-dir "$PWD" --base origin/develop --dry-run`
- Golden set do chat (`review/chat-golden/`): `npm run chat-evals -- --offline` roda o `ChatService` com o provedor roteirizado, nos seis modos (casos de rascunho declaram `mode`); com `PORTAL_LLM_*` no ambiente e sem `--offline`, roda com o modelo e mostra acerto, fonte citada, ferramenta, latência e tokens por pergunta.

## Fluxo de trabalho (comum ao time)

- Gitflow: `develop` é a base de trabalho; `main` é produção. Nunca commitar direto em nenhuma das duas.
- Branch: `tipo/CHAVE-123-slug` (tipos: feat, fix, chore, docs, hotfix, refactor, test, ci; slug de 2 a 4 palavras em kebab-case), sempre a partir de `develop` atualizada.
- Commits e título do PR em Conventional Commits.
- PR para `develop`, template preenchido: linha **Task** com a chave, Contexto de negócio, O que mudou, Como testar. SQL obrigatório quando o diff mexe em migration; ENV obrigatório quando mexe em `.env.example`.
- PR para `main` só sai de `develop` (release) ou de `hotfix/*`. Hotfix volta para `develop`.
- Merge só pela merge queue, com squash.
- Mudança de comportamento atualiza a documentação do módulo antes do merge. Módulo novo entra no catálogo.
- Módulo novo pode ser cadastrado no próprio PR que o cria. O bot lê o catálogo da base e do PR; para módulo que já existe, dono, tier e página valem da base e o PR só acrescenta caminhos.

## Padrões deste repo

- Toda regra de negócio nova tem teste que falha se a regra for removida.
- Migração de banco compatível com a versão anterior (expandir e contrair) e com restrição no banco quando a regra for de integridade.
- Fontes do Atlassian só usam `ReadOnlyHttp`; escrita só via `propose`, com confirmação.
- O bot só comenta; nenhum caminho de código aprova, pede mudanças ou mergeia.
- Mudança em `review/` ou em `tools/review-bot/src/` recebe `risk:ai-behavior` e passa pelo golden set.
- Mudança em `apps/portal-api/prompts/` recebe `risk:ai-behavior` e passa pelo golden set do chat (`npm run chat-evals`).

## Regras de código (comum ao time)

- TypeScript strict. `any` proibido; inferir tipos de schemas Zod quando existirem.
- Identificadores em inglês; documentação, mensagens e PRs em português.
- Erros com early return e tratamento explícito; nunca catch vazio.
- Código sem comentário solto; quando algo não é óbvio, JSDoc curto na função.
- Segredos só via env ou secret do CI. Nada de token, chave ou URL interna no código.

## O que NÃO fazer

- NÃO commitar ou mergear direto em `main` ou `develop`.
- NÃO usar `any`, `@ts-ignore` ou `eslint-disable` sem justificativa no PR.
- NÃO desligar teste ou usar `--passWithNoTests` para o CI passar.
- NÃO commitar `.env`, credenciais, `console.log` de debug ou código comentado.
- NÃO adicionar dependência nova sem justificar no PR.
- NÃO abrir PR sem a chave da task nem com o template vazio.
- NÃO colocar código, dado ou credencial de empresa neste repositório: ele é público.
- NÃO usar a fonte `atlassian` do bot no CI.
- NÃO deixar o agente de IA commitar sem ler o diff. O autor do PR é dono do código, gerado por IA ou não.
